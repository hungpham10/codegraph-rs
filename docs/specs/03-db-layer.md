# Spec 03 — Storage layer

**Status**: ✅ done — implemented in `crates/codegraph-graph/src/storage.rs`
(+ `storage/{sqlite,lmdb,redis,postgres,mysql}.rs`). The originally planned
`codegraph-db` crate was folded into `codegraph-graph` behind a trait, and
FTS5 was replaced by in-memory radix engines.

## Goal

Pluggable persistence for the semgraph: entities (symbols, chains, call
records, files, embeddings) + chain radix streams, with one file-local
default (SQLite) and optional network / multi-tenant backends.

## Design

```rust
pub trait Storage: Send + Sync { /* async trait, default no-ops */ }
pub trait Tx: Send { /* atomic radix mutations */ }
```

Two responsibilities:

1. **Entity store** — `save_symbol` / `load_all_symbols`, `all_chains`,
   call records per function, the inverted call-name → call-sites index,
   `upsert_file` / `load_all_files`, embeddings
   (`save_embedding` / `load_all_embeddings` / `knn`), `version` /
   `set_version`, `clear_entities`.
2. **Chain engine streams** — radix tree nodes/children/shard roots +
   per-function chain streams (`u64` LE), with optional bloom-filter
   acceleration (`bloom-search` feature).

Query logic never talks to storage directly — everything goes through
`GraphIndex`, which keeps in-memory maps (`symbols`, `name_index`,
`scope_index`, `chains_map`, `call_names`, `edges`) as the source of truth
and rebuilds them on open.

## Backends

| `type` in `config.toml` | Feature | Implementation |
|---|---|---|
| `sqlite` (default) | `sqlite` | sqlx, bundled SQLite (WAL), optional sqlite-vss KNN |
| `lmdb` | `lmdb` | `lmdb-rkv`, memory-mapped KV |
| `redis` | `redis` | redis `async`, requires explicit DSN |
| `postgres` / `mysql` | `postgres` / `mysql` (or `rdbms`) | sqlx, multi-tenant sharded by `repo_id` |
| — (in-process) | — | `InMemoryStorage` (tests, `GraphIndex::in_memory()`) |

Opening: `GraphIndex::open(dsn)` dispatches on the DSN scheme
(`sqlite://`, `lmdb://`, `redis://`); a scheme-less path only works when
exactly one persistent backend is compiled. `StorageRoute` (in
`codegraph-core`) describes how to open: `Memory`, `Local(dsn)`, or
`Sharded { dsns, repo_id, root }` with shard = `repo_id % len(dsns)`.

## Postgres / MySQL (multi-tenant)

Every table is partitioned by a leading `repo_id` (random `u64` generated by
`codegraph init`, self-healed on open). Schema is applied manually from
`sql/<engine>/` (`001-initial-schema.sql`, `002-add-repos-registry.sql`) —
no migrations run from the binary. Full design in `sql/README.md`.

## Validation

- `crates/codegraph-graph/tests/{sqlite,lmdb,rdbms,redis}.rs` — reopen
  round-trips (ingest → reopen → same query results), sharded DSN selection,
  repo_id partitioning.
- `crates/codegraph-bench` storage benches + `docs/benchmarks/storage-perf.md`.

## Deviations from the original spec

- No FTS5: name search is an in-memory radix `Search<u8>` over lowercase
  names, rebuilt on open/ingest — sub-millisecond and backend-independent.
- No incremental `sync`: `ingest` always resets and rebuilds (full re-index).
- rusqlite was replaced by sqlx so one driver stack serves SQLite + RDBMS.
